# API ルール（Nuxt.js Server API / Nitro）

## 設計方針

- Nuxt 3 の Nitro サーバーエンジンによる Server API を使用する。ルーティングは**ファイルパスと HTTP メソッドサフィックス**で決まる（`server/api/tasks/index.get.ts` → `GET /api/tasks`）。
- **ビジネスロジックはハンドラーに書かない**。ハンドラーは「入力の取り出し → ロジック呼び出し → ステータス設定 → エラーのマップ」に限定し、薄く保つ（実装例: [`server/api/tasks/index.post.ts`](../../apps/task-app/server/api/tasks/index.post.ts)）。
- ロジックの置き場は現状 `server/utils/`（`tasks.ts` に CRUD ロジックを集約）。**ドメインが 2 つ目に増えた時点で `server/services/` を切り、ドメイン単位でファイルを分ける**。
- すべての DB 読み書きは Server API 経由で行う（クライアントから直接 DB にアクセスしない）。
- **セキュリティ境界**: DB 接続情報・外部 API のシークレットは Server API 側に閉じ、クライアントへ露出しない。`runtimeConfig`（サーバ専用）に機密を置き、`runtimeConfig.public` には公開可の値のみ置く。
- レスポンスは DB の行をそのまま返さず、必要なフィールドに厳選して返す（後述）。

## 外部 I/O は引数で受け取る（テスト可能性）

- DB ハンドルは**モジュールから直接掴まず、引数で受け取る**。ロジック関数は `Queryable` インターフェースを受け取り、本番は `pg.Pool`、テストは `pg-mem` を注入する（[`server/utils/tasks.ts`](../../apps/task-app/server/utils/tasks.ts)）。
- **ハンドラーが `getPool()` を呼び、ロジック関数へ渡す**。この 1 段の分離が、実 DB なしでビジネスロジックを検証できる根拠になっている（`testing.md`「ビジネスロジックをモックしない」）。

## 型定義

- 型は**原則 `type`** を使う（`typescript.md`「type vs interface」）。
- 置き場所は**参照範囲**で決める。1 ファイル（ハンドラー）に閉じる型はコロケーション、**クライアントと Server API の双方から参照される API 契約の型は `types/` へ集約**して 1 箇所定義にする（同じレスポンス形を二重定義しない）。
- **共通定数は `constants/` に集約する**（`typescript.md`「定数の配置」）。マジックナンバー・マジック文字列を直接書かない。

## ディレクトリ構成

```
apps/task-app/server/
├── api/               # API エンドポイント（薄い）
│   └── tasks/
│       ├── index.get.ts
│       ├── index.post.ts
│       ├── [id].patch.ts
│       └── [id].delete.ts
├── middleware/        # サーバーミドルウェア（現状なし）
└── utils/             # DB 接続・ロジック・HTTP マップ・ロガー
```

## レスポンス整形（DB の行を素通ししない）

- **DB の行オブジェクトをそのまま返さない**。**公開してよいフィールドだけを厳選**したレスポンス型に変換して返す（内部 ID・監査カラム・他ユーザー情報を漏らさない）。
- 変換は明示的に行う（`mapRow` のようなマッパー関数）。**スプレッド（`{ ...row }`）で組み立てない** — カラムが増えた瞬間、自動的に公開される。
- SQL 側でも取得列を絞る（`SELECT *` を使わず列を列挙する）。**取らない・返さないの二重で絞る**。
- エラーレスポンスも整形する。**スタックトレース・SQL・内部メッセージをそのまま返さない**（`error-handling.md`）。500 は固定文言を返し、詳細はログとトレースに残す。
- **変換は Server API に閉じる。クライアント側で再変換しない**（`frontend.md`「型の扱い」と対になる規定）。
- **`server/` から `components/` `composables/` を参照しない**。サーバー層がクライアント層に依存してはならない。
- **理由**: 過剰公開（over-fetching / 機密漏洩）の防止、内部スキーマ変更がクライアント契約に直接漏れない疎結合化、転送量の削減。

## バリデーション

- 入力検証は **Server API 側を最終ゲート**とする。クライアント側の検証は UX 目的であり、これに依存しない。
- 検証の担当レイヤは 1 つに決める。本プロジェクトではロジック層（`server/utils/tasks.ts`）が担い、**ハンドラーには検証を書かない**（二重定義を避ける — `duplication.md`）。
- 検証失敗はドメインエラー（`TaskValidationError`）として投げ、HTTP へのマップは `toHttpError` に一任する。ハンドラーで直接 `createError` を組み立てない。

## 共通方針

- RESTful 設計（リソース指向エンドポイント）。レスポンス形式は JSON。
- ステータスコードは [`07-api-specification.md`](../../docs/07-api-specification.md) の定義に従う（作成は 201、更新・取得は 200、削除は 204）。
- **SQL インジェクション防止**: パラメータバインディング（`$1`）を使用し、文字列結合でクエリを構築しない。動的な `SET` 句を組み立てる場合も、値は必ずプレースホルダで渡す（`security.md`）。

## 計装（本プロジェクト固有）

監視基盤の題材であるため、**API 層はテレメトリの発生源として扱う**。

- HTTP と pg のスパンは**自動計装が生成する**。手動でスパンを張らない（重複スパンになる）。ビジネス上の意味を足したい場合は、既存のアクティブスパンに属性を追加する。
- ログは [`server/utils/logger.ts`](../../apps/task-app/server/utils/logger.ts) の `logger` を使う。`console.log` を直接呼ばない — **アクティブスパンからの trace_id 付与が効かず、ログとトレースの相関が切れる**。
- ログ属性に機密を載せない。オブジェクトを丸ごと渡さない（`security.md`「テレメトリに機密を載せない」）。
- **エラーは握り潰さない**。捕捉したら必ずログに残し、HTTP エラーとして再送出する。握り潰すとスパンが正常終了扱いになり、RED メトリクスのエラー率にも計上されない。
