## テスト戦略

監視基盤（Collector/Grafana 等）は設定ファイル中心のため、自動テストの主対象は **example アプリのタスク CRUD ロジック**とする。監視スタックは E2E 手順（[`02` 受け入れ条件](./02-requirements-specification.md#受け入れ条件)）で確認する。

| レイヤー | ツール | 対象 |
|----------|--------|------|
| ユニット/結合 | Vitest + pg-mem | `server/utils/tasks.ts` の CRUD ロジック（実 SQL を pg-mem で実行） |
| 手動 E2E | Docker Compose + Grafana | 3 本柱の相互リンク・ダッシュボード描画（受け入れ条件） |

**pg-mem を採用する理由**: インメモリで実 SQL を実行するため、ビジネスロジック（クエリ・バリデーション）を一切モックせず、外部 I/O（DB 接続）だけを差し替えられる。testing.md の「ビジネスロジックをモックしない／モックは外部 I/O のみ」に合致する。

## テストケース

正常系 1 : 異常系（準正常系 + 異常系）2 以上の比率を満たす。

| # | ケース | 分類 |
|---|--------|------|
| 1 | タスクを作成すると id/createdAt が採番され done=false で返る | 正常系 |
| 2 | 一覧取得が created_at 昇順で返る | 正常系 |
| 3 | done を true に更新すると当該タスクのみ更新される | 正常系 |
| 4 | タスクを削除すると一覧から消える | 正常系 |
| 5 | 空文字 / 空白のみの title での作成は拒否される（バリデーションエラー） | 準正常系 |
| 6 | 存在しない id の更新はエラー（未存在）になる | 準正常系 |
| 7 | 存在しない id の削除はエラー（未存在）になる | 準正常系 |
| 8 | done に真偽値以外を渡すと拒否される（型不正） | 準正常系 |
| 9 | 更新項目が一つもない PATCH は拒否される | 準正常系 |
| 10 | DB 接続/クエリ失敗時にエラーが伝播し握り潰されない | 異常系 |

> 正常系 4 : 異常系（準正常系 + 異常系）6 = おおむね 1 : 1.5。実装時に異常系を補強して 1 : 2 以上を担保する。

## カバレッジ目標

- `server/utils/tasks.ts`（CRUD ロジック）のブランチを重点的に担保する。
- バリデーション分岐（title 空・型不正・未存在）を必ずケース化する。
- 数値目標より「仕様分岐の網羅」を優先する。

## テストツール・実行方法

- 実行: ルートで `pnpm test`（内部で task-app の Vitest を起動）。
- CI 連携は現状スコープ外（将来 GitHub Actions 等で `pnpm test` を回す想定）。

## 原則

- テストは仕様の証明。テストが失敗したら**実装を直す**（テストを実装に合わせない）。
- 正常系 1 : 異常系 2 以上を目安にする。
- ビジネスロジックをモックしない。モックは外部 I/O（DB/HTTP/FS）のみ（本プロジェクトでは DB を pg-mem に差し替え）。
- `toBeTruthy()` 等の曖昧なアサーションを避け、具体的な値（id の存在・done の真偽・配列長・並び順）で検証する。
