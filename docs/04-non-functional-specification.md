## パフォーマンス要件

- ローカル開発機で `docker compose up -d --build` 後、概ね 1〜2 分以内に全サービスが healthy になることを目安とする。
- アプリの API レスポンスは通常時 100ms 程度（DB クエリ含む）を目安。トレースのレイテンシ観測が主目的で厳密な SLA は設けない。
- テレメトリはバッチ送出（OTLP）し、操作からおおむね数秒〜十数秒で Grafana 上に反映される（Collector/各バックエンドの flush 間隔依存）。

## 可用性・信頼性

- 単一ホスト・単一インスタンス構成。高可用は持たない（学習用途）。
- 各サービスは Compose の `restart: unless-stopped` と healthcheck により、依存順（postgres → task-app、collector → backends）で起動させる。
- データ保存はバックエンドごとの named volume。長期保存・バックアップは行わず、`docker compose down -v` で破棄できることを許容する。

## エラーハンドリング・堅牢性

| 状況 | 振る舞い |
|------|----------|
| Collector が未起動 / 送出失敗 | アプリは OTLP 送出をリトライしつつ通常処理は継続（テレメトリ欠落のみ）。アプリ機能は停止しない |
| PostgreSQL が未起動 | task-app は healthcheck/依存により起動を待機。接続不可時 API は 5xx を返す |
| 不正な API 入力 | 400（バリデーション）を返し、トレース/ログにエラーとして記録される |
| 存在しないリソース操作 | 404 を返す |
| バックエンド（Tempo/Loki/Prometheus）障害 | 該当シグナルのみ欠落し、他シグナルとアプリ機能には波及しない |

## ユーザビリティ要件

- example アプリは PC ブラウザでの利用を主対象とし、過度なレスポンシブ対応は行わない。
- 操作結果（成功/失敗）は画面上で即時フィードバックする。
- Grafana はプロビジョニング済みデータソース/ダッシュボードにより、初回ログイン直後から監視を開始できる。

## 対応環境

- **ホスト**: macOS（darwin）+ Docker / Docker Compose。Linux でも動作想定。
- **ブラウザ**: 最新の Chrome / Safari / Firefox。
- **ランタイム**: コンテナ内 Node.js 22 系（アプリ）、各監視コンポーネントは公式イメージの安定版。
